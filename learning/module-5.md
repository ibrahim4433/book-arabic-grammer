# Module 5: The HTML Engine & The 1-Page Law

Welcome to Module 5. By now, you know how Python strings together HTML snippets, how the Control Room operates, and how the AI extracts the Arabic text. 

But generating a long HTML file is useless if we want to print a physical book. A webpage scrolls forever; a piece of A4 paper does not.

This repository enforces a strict **"1-Page Law"**. Every single HTML file inside the `pages/` directory must render perfectly onto exactly *one* A4 piece of paper. It cannot overflow onto a second page, and it cannot be too empty (Underflow).

In this module, we will explore the tools built specifically to enforce this mathematical law. We will look at how the HTML is tracked, validated, and finally compiled into a PDF.

## Beginner Primer: Command Line Arguments (`argparse`)

In previous modules, we ran Python scripts simply by typing `python system.py`. But what if we want to run a script and pass it a specific file to check, like: `python verify_layout.py pages/01.html`?

How does the Python script grab that `"pages/01.html"` string from the terminal? It uses a built-in library called `argparse`. 

You will see this at the bottom of almost every utility script in this repository:
```python
# From verify_layout.py
import argparse

if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="Verify 1-Page Layout")
    # This tells Python to expect a file path after the script name
    parser.add_argument("html_file", help="Path to the HTML file")
    
    args = parser.parse_args()
    # Now the script can use args.html_file to open the document!
    check_layout(args.html_file)
```
Whenever you see `argparse`, just remember it is the bridge between the terminal commands you type and the variables inside the Python script.

## Lesson 1: The Dual Builders (`build.py` vs `build-with-id.sh`)

When it's time to take the hundreds of `.html` files in `/pages/` and turn them into `book.pdf`, developers have two options. Why are there two?

### 1. The Standard Builder (`build.py`)
This is the modern, integrated script. It assumes your current virtual environment (`.venv`) is healthy and has `weasyprint` installed with all its complex C-libraries (GTK/Pango).

```python
# From build.py
def build_book(config: BuildConfig) -> BuildResult:
    # ...
    try:
        from weasyprint import HTML
    except ImportError as exc:
        raise BuildError("WeasyPrint is not installed.") from exc
    except OSError as exc:
        raise BuildError(
            "WeasyPrint is installed, but its native GTK/Pango libraries are missing."
        ) from exc
```
`build.py` takes all the HTML files, wraps them in a master template (adding the watermark "أ. حنا خفيف"), and uses `weasyprint` to render the massive PDF in one shot.

### 2. The Isolated Builder (`scripts/build-with-id.sh`)
Rendering PDFs is notorious for crashing environments. If a developer accidentally breaks the main `.venv`, they can't build the book. To solve this, a legacy/isolated shell script is provided:

```bash
# From scripts/build-with-id.sh
if [ ! -d "venv" ]; then
    python3 -m venv venv
    echo "    Created new virtual environment."
fi
./venv/bin/pip install -r requirements.txt
./venv/bin/python debuging/build-with-id.py
```
This script creates an entirely separate, isolated `venv` (not `.venv`), installs the absolute minimum requirements, and runs a secondary script. This is the "safe fallback" when the main environment is acting up.

## Lesson 2: ID Management (`id_manager.py`)

If a page overflows by 3 millimeters, how do you know *which* paragraph to shrink or delete? You can't just tell a Python script "shrink the third paragraph." It needs absolute, unique identifiers.

Every significant HTML block in this project must have a unique ID in the format `bXXXXX` (e.g., `id="b14923"`).

To manage this, the system relies on `Jules-workspace/id_manager.py`.

### Real Code: Generating Cryptographic IDs

When you run `python Jules-workspace/id_manager.py auto-tag`, the script scans every HTML file. If it finds a block missing an ID, it generates one:

```python
# From id_manager.py
import secrets

    def generate_id(self) -> str:
        """Generate a cryptographically random unique ID in format bXXXXX."""
        while True:
            # 5 decimal digits → 100_000 possibilities, collision-safe via set
            digits = "".join(str(secrets.randbelow(10)) for _ in range(5))
            new_id = f"b{digits}"
            if new_id not in self.existing_ids:
                self.existing_ids.add(new_id)
                return new_id
```

**Line-by-Line Breakdown:**
1.  **`import secrets`**: We do not use the standard `random` library. `secrets` provides cryptographically secure random numbers, minimizing the chance of two identical IDs being generated by two different agent processes running at the same time.
2.  **`secrets.randbelow(10)`**: Generates a random number from 0 to 9. We loop this 5 times.
3.  **`self.existing_ids.add(new_id)`**: The script keeps a master list of every ID in the repository in memory. If a collision *does* happen, it rejects the ID and loops again (`while True`).

Because of `id_manager.py`, every single grammar rule, exam question, and table can be targeted perfectly by our debugging scripts.

## Lesson 3: Validating the 1-Page Law (`verify_layout.py`)

How does Python know a web page will fit on physical paper *before* you print it? It uses `weasyprint` in a "headless" measuring mode.

Look at `Jules-workspace/verify_layout.py`:

```python
# From verify_layout.py
#: WeasyPrint renders at 96 DPI
PX_TO_MM: float = 25.4 / 96.0

#: A4 page height
PAGE_HEIGHT_MM: float = 297.0

#: Bottom margin in CSS is 9 mm
PRINTABLE_BOTTOM_MM: float = PAGE_HEIGHT_MM - 9.0

#: If blank space exceeds this % of page height, it's UNDERFLOW
UNDERFLOW_THRESHOLD_PCT: float = 10.0
```

### The Math of Rendering
When `verify_layout.py` runs, it asks `weasyprint` to draw the HTML in memory (without saving a PDF). It then loops through every single HTML box (paragraphs, headers) and measures its exact Y-coordinate in pixels.

It converts those pixels to millimeters using the formula `25.4 / 96.0`. 
*   If the lowest element on the page sits at `300.0` mm, the script knows it has breached the `297.0` A4 limit. It instantly throws an **OVERFLOW** error and rejects the page.
*   If the lowest element sits at `150.0` mm, the script calculates that the page is half empty. It breaches the `10.0` percent `UNDERFLOW_THRESHOLD_PCT`, throws an **UNDERFLOW** error, and demands the AI add more examples to fill the space.

## Lesson 4: Practical Debugging Exercise

Imagine an AI agent just generated a page (`pages/05.0_lesson.html`), and you are watching the Control Room logs.

Suddenly, you see this error:
```
[FAIL] pages/05.0_lesson.html
Error: OVERFLOW detected. Remaining height: -4.2 mm.
```

How do you handle this? You do not open the file and blindly delete text.

### The Debugging Flow:
1.  **Check the ID:** You run `verify_layout.py` manually with a verbose flag. It will tell you: `"Overflow caused by element b83291"`.
2.  **Locate the Block:** Because `id_manager.py` did its job, you open `pages/05.0_lesson.html` and search for `b83291`.
3.  **The Fix:** You see that `b83291` is a large "Benefit Box" (`.benefit-box`). 
4.  **The Resolution:** You have three choices:
    *   **Condense:** Shorten the Arabic text slightly.
    *   **Split:** Move `b83291` to a brand new file called `pages/05.1_lesson.html`.
    *   **CSS Tweaks:** Check if a previous element has an unnecessary `mb-5mm` (5 millimeter margin-bottom) class pushing everything down.

By strictly enforcing the 1-Page Law mathematically, the final PDF generation (`build.py`) becomes flawless. There are no awkward page breaks cutting sentences in half, because every single HTML file is pre-calculated to fit a single piece of paper perfectly.
